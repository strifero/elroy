# Chapter 7: Teaching it to answer

By the end of this chapter Elroy replies to "write a function that checks whether a number is prime" with a function that checks whether a number is prime, says who it is when asked, and stops talking when it is done. The base model could do none of those things, and the change took 93 minutes on one GPU.

## Why a base model does not answer questions

Pretraining teaches the model to continue text. Give it `def is_prime(n):` and it writes a body, because files that start that way continue that way. Give it `Write a function that checks whether a number is prime.` and it continues with whatever tends to follow that sentence in the corpus; in Chapter 5 that was a comment explaining what a prime number is, and then silence. The knowledge is there. The format is not.

Supervised fine-tuning shows the model a few tens of thousands of conversations laid out in one fixed template and trains it to produce the reply part. It learns three things: the template means a question is being asked, the reply should be an answer, and `<|end|>` means stop.

## The template

```
<|system|>You are Elroy, a small Python assistant built from scratch by Strife Technologies.<|end|>
<|user|>{question}<|end|>
<|assistant|>{answer}<|end|><|endoftext|>
```

`elroy/chat.py` has it in one place, `build_prompt`, used identically for training data and for inference. The special tokens were reserved in the tokenizer in Chapter 2 so they are single ids the model has never seen in pretraining; it learns them from scratch here.

## The data

```bash
python scripts/prepare_sft.py --tokenizer data/tokenizer.json --out data/sft
```

Two public sets, both permissively licensed: Magicoder OSS-Instruct (problems generated from real open-source snippets, MIT) and evol-codealpaca-v1 (Evol-Instruct style tasks, Apache-2.0). The script keeps examples whose reply has a Python code block that parses under Python 3 and fits in 2048 tokens under the template. That kept 36,964 of OSS-Instruct's 38,284 Python examples and 47,002 of evol-codealpaca's 111,272 (the rest are other languages, or replies whose code does not parse).

Plus `sft/handwritten.jsonl`: 45 examples we wrote, repeated four times, 180 rows. Who Elroy is, what it cannot do, a dozen beginner concepts, a dozen small functions. Every base model fine-tuned only on scraped data believes it is ChatGPT; this is the cheap fix. The file is generated by `sft/make_handwritten.py` so the source of truth is readable Python, and every code block in it is checked with `ast.parse`.

Total: 82,464 training examples and 1,682 held out, mean 526 tokens each, 25.2M supervised tokens. That is 0.1% of the pretraining budget.

### Loss masking

`format_example` returns the token ids and a mask that is 0 over the system and user text and 1 over the reply and its `<|end|>`. `Elroy.forward` takes that mask and averages the loss over the 1s only. The model is never trained to predict the question, only the answer. Without this, a third of the gradient goes into learning to write user prompts, which is both wasted and slightly harmful.

## Training

```bash
python -m elroy.sft --base checkpoints/elroy-350m/base-final.pt --data data/sft --out checkpoints/elroy-350m-chat
```

Same model class, same optimizer, same bf16 autocast. Differences from pretraining: learning rate 5e-5 instead of 4e-4 (the weights are good; we are nudging, not carving), two epochs, no weight decay, 32 examples per optimizer step as 4 per micro-batch times 8 accumulation steps, and batches drawn from length buckets so that padding to the longest example in a batch wastes little.

Two things from the pretraining chapters applied here too. The checkpoint is loaded to CPU and the dict dropped before training starts, for the reason Chapter 4 explains. And `micro_batch` 8 does not fit a 20GB card at 2048 tokens; 4 does.

5,154 steps, 93 minutes on one A4500 with `torch.compile(dynamic=True)` because the batch shapes vary. The held-out loss, measured on the reply tokens only:

```
before     1.3324
step  200  1.0335
step  400  1.0165
step 1000  0.9891
step 2000  0.9585
step 3000  0.9464
step 4000  0.9409
step 5154  0.9404
```

Most of the gain is in the first 200 steps, which is the model learning the template. The rest is the slow part: learning what a good answer to a programming question looks like. The curve is flat by the second epoch, and a third epoch would start memorizing.

## What changed

Same questions to the chat model that the base model failed in Chapter 5. `scripts/sample_chat.py` runs a fixed set; the full output is in `results/chat/samples.md`.

The prose request that produced a comment and nothing else from the base model:

> **user:** Write a Python function that checks whether a number is prime.
>
> **elroy:** [a correct `is_prime` using the 6k±1 trick, then an explanation, then usage examples claiming `is_prime(2)` is `False` and `is_prime(5)` is `False`]

The function is right; the examples under it are wrong. It has learned that answers end with examples, not what the examples should say, and nothing about it has a way to run the code. This is the single most important thing to know about the model.

`word_counts`, which the base model got subtly wrong, is now right: it lowercases first, splits, and counts with a dictionary. Then it appends an example output for the sentence "Hello, how are you? I am fine, thank you!" that lists words not in the sentence. Same pattern.

Identity works, from the 45 handwritten examples:

> **user:** Who are you?
>
> **elroy:** I am Elroy, a small Python assistant. I was built from scratch as a teaching project by Strife Technologies: a 360 million parameter transformer trained on educational Python and English. I can write short Python functions, explain beginner concepts, and complete code inside a file. I am not a general assistant and I make mistakes, so run what I write.

That is close to verbatim from the file, and so is its answer to the list-versus-tuple question, which is a good answer because we wrote a good answer and showed it four times. Ask "What can you not do?" and it misses the handwritten reply and launches into a triangle-area script instead: four repetitions of 45 examples against 82,000 others is enough to plant an identity, not enough to make every one of them reliable.

Anything outside Python is where it should not be used, and the fine-tuning makes that more dangerous, not less, because the answers now arrive in a confident helpful register. Asked for the capital of France it said Londres, with a print statement demonstrating it. Asked about Providence it produced a fabricated fact sheet (population 3,000, a small island in the middle of the United States) and then repeated a population-density line until the token limit. The base model looped on Providence too. The chat model loops in a table.

And the `<|end|>` lesson: the model stops now, which is the whole point, and in the first hour of use it stopped too well. A lowercase "hi" got an empty reply: the handwritten set has "Hi" and "Hello!", three greetings in all, and against 82,000 programming questions that was not enough for the model to generalize to a different capitalization, so the most likely first token after `<|assistant|>` was `<|end|>`. The chat server in Chapter 8 refuses to stop before three real tokens, which turns the empty reply into "Hello, how can I help with this?". The honest fix is more greeting variants in the handwritten set, and it is a good illustration of how thin the layer that makes a model conversational really is.

## Evaluation

```bash
python scripts/eval_code.py --ckpt checkpoints/elroy-350m-chat/chat-final.pt --bench humaneval --chat
```

In chat mode the harness poses each problem as a user message, extracts the first code block from the reply, and runs the tests. Greedy decoding, same sandbox as Chapter 5.

| Benchmark, pass@1 | Base | Chat |
|---|---|---|
| HumanEval | 13.4% | 26.8% (44 of 164) |
| HumanEval+ | 11.0% | 25.6% (42 of 164) |
| MBPP (sanitized) | 20.2% | 38.9% (100 of 257) |

Fine-tuning doubled every number, and 25.2M supervised tokens did it. That is not because the model learned more Python in 93 minutes; it is because the base model was leaving points on the table through format. Look at where the base model's HumanEval failures went: 15 syntax errors, mostly completions that ran past the end of the function and hit the token limit mid-statement. The chat model has 4. The base model got nothing past problem 61; the chat model passes 11 problems in the harder half of the set, up to problem 162. It also gives up two the base model had, which is normal variance at this scale. Of the 44 chat passes, 20 are problems the base model also solved and 24 are new.

HumanEval+ tells the same story with less slack: 25.6% against 26.8% is a 4% relative drop, where the base model dropped 18%. The chat model's solutions are more often fully correct rather than correct on the visible cases, most likely because the instruction data is full of complete functions with edge cases handled, and that is what it now imitates.

MBPP needed its prompt fixed before the number meant anything. The first chat run scored 2.5% on the first 40 problems, and every failure was the same: the task text ("Write a function to find the shared elements from the given two lists") does not name the function, the model picked its own name, and the hidden tests called `similar_elements`. The standard MBPP prompt from the original paper shows the three test assertions to the model for exactly this reason, and with them included the chat model scores 38.9%. The base model got the tests too, inside the docstring, so the comparison is fair. Prompt format is worth more than a few points on this benchmark, which is a reason to read the harness before quoting anyone's number, including ours.

What did not change is the shape of the failures. 102 of the 120 HumanEval failures and 122 of the 157 MBPP failures are assertion errors: code that runs and returns the wrong thing. That is the same failure the samples show, and no amount of format training touches it. It is a function of the model's size and its 20B tokens, and the honest summary of the chat model is that it writes correct short Python about a quarter to two fifths of the time on a first attempt, with no way of knowing which times.
